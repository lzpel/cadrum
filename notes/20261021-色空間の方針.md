# 色空間の方針 / Color space policy

STEP の色には色空間を仮定しない。ISO 10303-46 の `COLOUR_RGB` は色空間を定めていないので、値をどの色空間で解釈するかは利用者に任せる。
cadrum has no assumption about the colour space of STEP colours. ISO 10303-46 does not define one for `COLOUR_RGB`, so the user decides how to read the values.

STEP と `struct Color` は同じ色空間にあるとみなす。`COLOUR_RGB` の値は変換せずにそのまま `struct Color` の r, g, b になり、書き出しでもそのまま戻る。
STEP and `struct Color` share one colour space. `COLOUR_RGB` values become `struct Color`'s r, g, b unconverted, and are written back unconverted.

OCCT による STEP との間の色変換は意図的に止めている。OCCT の `EncodeColor`/`DecodeColor` は `Quantity_Color` を linear とみなして sRGB との変換をするので、cadrum は `Quantity_Color` に値を `Quantity_TOC_RGB` で素通しで入れ、`StepVisual_ColourRgb` を自分で読み書きする（`src/ffi.cpp`）。例外は成分がすべて 0 か 1 の名前付き8色（`DRAUGHTING_PRE_DEFINED_COLOUR`）で、0 と 1 は変換しても値が変わらないので OCCT を通す。
cadrum deliberately suppresses OCCT's colour conversion at the STEP boundary. OCCT's `EncodeColor`/`DecodeColor` treat `Quantity_Color` as linear and convert to and from sRGB, so cadrum stores values in `Quantity_Color` as-is with `Quantity_TOC_RGB` and reads and writes `StepVisual_ColourRgb` itself (`src/ffi.cpp`). The exception is the eight pre-defined colours (`DRAUGHTING_PRE_DEFINED_COLOUR`), whose components are all 0 or 1; conversion leaves 0 and 1 unchanged, so they go through OCCT.

STEP 以外の出力は、例外として `struct Color` が sRGB だったと仮定する。SVG と PNG は値をそのまま `*255` し、glTF は spec が linear を求めるので `Color::to_linear` で変換してから `baseColorFactor` に書く（#307, PR #314）。
Outputs other than STEP assume, as an exception, that `struct Color` is sRGB. SVG and PNG scale the values by 255 as they are, and glTF, whose spec requires linear values, converts them with `Color::to_linear` before writing `baseColorFactor` (#307, PR #314).
